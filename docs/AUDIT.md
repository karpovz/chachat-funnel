**D1 — P2. Два первых запроса могут разорвать анонимную историю.**

Место: `src/server/session.ts:25–41`, `src/components/Funnel.tsx:28–30`, `src/hooks/funnel-api.ts:7`.

Два `POST /api/session` до получения cookies независимо создают visitor/session. Ответ B позднее заменяет cookies всего браузера, тогда как вкладка A продолжает хранить sessionId A. Следующие API A авторизуются cookies B. Уже записанные в A события остаются вне истории пользователя, разрешенного в B.

Воспроизведено на реальном API с управляемым порядком применения Set-Cookie: отправлены два запроса без cookies; записан view с cookies A; применены cookies B; пройдены quiz/email. Получены разные sessionId; первая сессия сохранила `user_id = null`; запрос первой истории через нового пользователя вернул 0 событий. Это моделирование порядка ответов через HTTP, а не полная браузерная проверка одновременного первого открытия.

Исправление: определить один протокол bootstrap для вкладок — координация первого запроса, повторная проверка состояния после захвата блокировки и согласование активной session identity. Серверная защита checkout должна сохраниться. Регрессия должна начинаться с отсутствующих cookies; текущие DB fixtures сразу создают готовые email/paywall-сессии и этот участок обходят.

**D2 — P2. Старый polling откатывает новую попытку и удаляет ее ключ.**

Место: `src/components/Checkout.tsx:23–34`, `src/components/Checkout.tsx:50–58`.

Первый сценарий: GET текущей покупки начинает читать предыдущий `failed`, ответ задерживается; retry получает `processing` для attempt 2; затем приходит старый GET с `failed` для attempt 1. UI принимает его, показывает старый decline, включает Submit и очищает idempotency key, хотя сервер еще обрабатывает attempt 2.

Второй сценарий: вкладка B сохраняет новый ключ в общем localStorage и начинает POST; polling вкладки A видит предыдущее failed-состояние и безусловно удаляет ключ B.

Оба сценария воспроизведены в Chromium с управляемыми API-ответами. Это нарушение клиентского восстановления, а не доказательство двойного списания: серверная уникальность покупки и processing-attempt продолжает защищать БД.

Исправление: применять ответы с проверкой поколения запроса/номера попытки, отменять устаревшие проверки и удалять только ключ соответствующей завершенной попытки. Добавить тесты reorder-ответов и общего storage двух вкладок. Серверный ответ может потребовать идентификатор попытки для однозначной связи с локальным ключом; такое расширение сначала зафиксировать в контракте.

**D3 — P2. Install может подтвердить покупку для устаревшего email.**

Место: `src/components/Funnel.tsx:100–102`, `src/components/Funnel.tsx:115`.

A и B открыли paywall с первым email. B вернулась на email до создания purchase, сменила адрес и оплатила. Серверный владелец и B используют новый email. A получает purchase success через polling, но `completed()` оставляет прежний `session.email`; на Install отображается старый адрес. Воспроизведено в двух Chromium-вкладках с mock API.

Исправление: перед подтверждением Install обновлять авторитетный PublicSession либо включать подтвержденного получателя в публичный purchase response. Проверить межвкладочную смену email до checkout и неизменность владельца после создания purchase.

**D4 — P2. Окончательная ошибка одного события блокирует последующую аналитику.**

Место: `src/hooks/funnel-api.ts:35–45`, `src/components/Funnel.tsx:77`, `src/server/funnel.ts:58–60`.

Пример: недоставленный `plan_selected` остался в sessionStorage; план позже отключили; событие получает `400 invalid_plan`. Оно остается первым в очереди навсегда. Последующие screen/payment/install events не доставляются. Если уже существующая paywall-сессия вернется на landing, Start тоже не пройдет: он ожидает успешного опустошения всей очереди перед переходом.

Воспроизведено mock Chromium: заполненная paywall-сессия открыта на `#landing`, перед ней в очереди старый plan_selected. После двух нажатий Start URL остается `#landing`, age_confirmed не принят, очередь растет. Привязка invalid_plan к отключенному каталогу подтверждена серверным кодом.

Исправление: различать временные сетевые/5xx ошибки и постоянные ошибки валидации, сохранять диагностируемый результат отклонения и продолжать допустимые события. Бизнес-переход подтверждения возраста не должен зависеть от доставки всей предыдущей телеметрии. Не удалять без разбора все 4xx: например, 401 требует восстановления сессии, а не потери истории.

**D5 — P2. План по умолчанию отсутствует в `plan_selected`.**

Место: `src/components/Checkout.tsx:8`, `src/components/Checkout.tsx:78`.

Annual выбран автоматически, но событие отправляется только в onChange. Два реальных успешных browser-сценария на Annual оставили 0 событий plan_selected. payment_submitted и purchase events есть, поэтому деньги и число покупок не теряются; недостоверна полнота истории выбора плана и сравнение поведения default/manual selection.

Исправление: согласовать контракт для автоматического выбора и отправлять событие при первоначальном выборе с защитой от повторного mount; полезно отличать default от ручного выбора. Регрессионный happy path должен проверять историю событий, а не только наличие Install.

**D6 — P2. Отключение зарезервированного тарифа лишает checkout возможности повторить оплату.**

Место: `src/server/payments.ts:58–61`, `src/server/funnel.ts:85`, `src/components/Checkout.tsx:69–77`, `src/components/Checkout.tsx:92`.

На реальном API: decline на Monthly; `plans.is_active=false`; новый idempotency key и success-card. Ответ — HTTP 400, хотя purchase содержит неизменяемый price snapshot. GET /plans больше не содержит Monthly. После refresh UI ищет выбранный snapshot только среди активных планов; selected отсутствует, Submit disabled, а выбор другого плана уже запрещен. Серверная часть воспроизведена; отключение кнопки следует из веток render. Активность плана восстановлена в finally.

Обычные три неизменяемых demo-плана не затрагиваются. Для сопровождения нужно явно решить lifecycle предложения: исполнять уже зарезервированный snapshot либо предусмотреть понятное закрытие предложения и новый доступный путь. Текущая ситуация «нельзя повторить и нельзя сменить план» должна быть исключена.

**D7 — P2 для сопровождения. Автоматической проверки изменений нет.**

Место: `package.json:15`, `tests/server/database.test.ts:18`, `Dockerfile:14`; CI-конфигурации в tracked files нет.

Обычный pnpm test пропускает все PostgreSQL-инварианты. Docker build компилирует, но не проверяет платежное поведение. Следующее изменение агента может пройти обычные команды со сломанной идемпотентностью. Наличие ручных PASS в README это не предотвращает.

CI не был обязательным пунктом исходного задания; это существенный разрыв именно с повышенным требованием пользователя к безопасной дальнейшей разработке. Нужен автоматический цикл lint/typecheck/unit → disposable PostgreSQL/migrations/invariants → production build/browser smoke. В инструкции агентам следует указать единый обязательный запуск этого цикла.

**D8 — P2 для сопровождения. Документированные DB-тесты не изолированы от приложения.**

Место: `README.md:80–85`, `compose.yaml:21`, `tests/server/database.test.ts:48–53`.

Команда README подключает tests к основному Compose DB. Один тест меняет общий Monthly amount на 12345 и затем восстанавливает. Одновременная ручная покупка может сохранить тестовую цену; аварийная остановка до finally оставляет измененное значение. Предупреждение не запускать browser tests одновременно снижает риск, но не создает изоляцию.

В этом аудите использована отдельная база. Для репозитория нужны disposable DB/project и воспроизводимая QA-команда, которой не требуется доступ к обычным данным разработчика.

**D9 — P2 для dependency maintenance. `pnpm audit` не чистый.**

Место: `pnpm-lock.yaml:2663–2666`: `prisma → @prisma/config → deepmerge-ts@7.1.5`.

`pnpm audit --json` вернул один high advisory: `GHSA-ggr8-5vv4-36mx` / `CVE-2026-40345`. Версии deepmerge-ts ниже 8.0.0 подвержены переполнению стека при слиянии циклических объектных графов. Обычный JSON сам по себе не создает это условие. [Advisory автора библиотеки](https://github.com/RebeccaStevens/deepmerge-ts/security/advisories/GHSA-ggr8-5vv4-36mx).

Транзитивная зависимость подтверждена, доступность атаки через API этой воронки не доказана. Это не основание объявлять приложение удаленно эксплуатируемым. Следует выбрать совместимое обновление цепочки Prisma, повторить проверки и включить dependency scan в CI. Без проверки совместимости принудительно подменять major транзитивной библиотеки не следует.

**Оценка архитектуры и актуальности.**

Next.js 16 относится к Active LTS; Node 22 остается LTS; PostgreSQL 16 поддерживается до 9 ноября 2028. Текущая архитектура App Router + тонкие route handlers + серверные сервисы + SQL-транзакции соответствует задаче. Необходимости переписывать проект ради новых номеров версий, Server Actions или отдельного backend не обнаружено. [Next.js support policy](https://nextjs.org/support-policy), [Node releases](https://nodejs.org/en/about/previous-releases), [PostgreSQL versioning](https://www.postgresql.org/support/versioning/).

Prisma 6 не является последним major: переход на 7 меняет конфигурацию, генерацию клиента, ESM и драйверы. Он должен быть отдельной проверенной задачей с учетом D9. [Официальная инструкция миграции Prisma 7](https://www.prisma.io/docs/orm/v6/more/upgrades/to-v7).

Сильные решения: database unique constraints на session purchase и idempotency key; partial unique processing index; row lock сессии вокруг связанных изменений; price snapshot и integer minor units; timestamptz; атомарные outcome events; безопасная граница fake processor; strict TypeScript без явных any; Zod на серверном входе. Результаты concurrency/retry тестов подтверждают эти решения.

Для дальнейшей поддержки нужны умеренные изменения структуры:

- Вынести управление checkout/recovery в явную модель переходов и отдельный hook; компоненты экранов оставить ответственными за отображение. Сложность D2 сейчас распределена по polling, refs, React state и localStorage.
- Полностью вынести copy/config из Funnel/Checkout. Сейчас вопросы отделены, но landing/paywall/install copy и большой SVG смешаны с навигацией. SPEC §4 выполнен в этой части частично.
- Устранить дублирование question IDs/options в `shared/contracts.ts`, `content/funnel.ts`, `server/funnel.ts`. Число вопросов в resolveEmail также захардкожено как 5. Нужен один типизированный источник допустимых ответов.
- Отформатировать JSX/CSS/payment service. Есть JSX-строки длиной до 2497 символов и CSS-строки до 6029 символов; это мешает человеку и агенту проверять небольшой diff. Добавить format-check после согласования инструмента.
- Заменить слепое приведение `payload.data as T` в API-helper проверкой публичных Zod-схем в критичных местах. Серверные payload уже проверяются; это улучшение клиентской надежности, не отсутствие серверной валидации.
- Добавить безопасную диагностику неожиданных ошибок: correlation ID, код/категория ошибки и операция без тел запроса, card fields или email. `src/server/http.ts:15–16` сейчас скрывает вообще всю причину HTTP 500.
- Для роста данных добавить индексы основных путей `funnel_sessions(user_id, started_at)` и visitor/session history. Текущие event indexes и платежные уникальности есть; массовое нагрузочное исследование планов SQL не проводилось.
- Определить время жизни/resume сессии и поведение при смене funnel_version. Сейчас существующая session cookie возобновляет ту же сессию, в том числе завершенную, до истечения cookie; «визит завтра» не отделяется по времени.
